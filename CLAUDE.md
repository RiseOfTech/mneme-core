# mneme-core — Руководство по проекту

Этот файл расширяет глобальные инженерные стандарты (`~/.config/opencode/AGENTS.md`).
Проектные правила ниже имеют приоритет, если конфликтуют с глобальными.

`mneme-core` — бэкенд-сервис продукта **Mneme**: он владеет доменом карточек,
интервальным повторением (Лейтнер) и публичным REST API. Продуктовый объём описан в
`PROJECT.md`; авторитетный дизайн — в `ARCHITECTURE.md`. Прочитай `ARCHITECTURE.md`
перед реализацией — если его нет, архитектура ещё не решена, поэтому не выдумывай
структуру, а спроси.

## Стек

- Язык: Java 21
- Фреймворк: Spring Boot 4.1 (Spring Framework 7, Jakarta EE 11, Jackson 3)
- Сборка: Gradle (Kotlin DSL)
- Хранение: PostgreSQL — **подход к хранению ещё не выбран** (см. правила)
- Group: `io.github.ifamneme`
- Корневой пакет: `io.github.ifamneme.mneme_core` (раскладка подпакетов — по `ARCHITECTURE.md`)

## Сборка и запуск

- Сборка: `./gradlew build`
- Тесты: `./gradlew test`
- Запуск: `./gradlew bootRun`
- Health (пробы k8s): `GET /actuator/health`

Запускай `./gradlew build` после любого значительного изменения, чтобы убедиться, что код компилируется и тесты проходят.

## Проектные правила

- REST-эндпоинты версионируются под `/v1`.
- НЕ добавляй зависимости хранения (Spring Data JPA/JDBC, драйвер Postgres,
  Flyway) и не моделируй ничего, что относится к базе данных, пока подход к хранению не
  решён в `ARCHITECTURE.md`. Это сделано намеренно — хранение является архитектурным
  решением, и JPA-сущности не должны протекать в верхние слои.
- НЕ выдумывай раскладку пакетов и модулей; она определена в `ARCHITECTURE.md`. До тех
  пор вноси в существующий каркас минимальные изменения.
- Этот репозиторий знает только свои модели. Он не разделяет библиотек моделей с другими
  сервисами (`mneme-ai`, `mneme-web`, `mneme-mobile`). Межсервисные контракты выражаются
  через OpenAPI/spec; внешние модели отображаются на наши на границе (anti-corruption layer).
- Генерация изображений НЕ входит в этот репозиторий — это отдельный сервис Phase 2
  (`mneme-ai`). В MVP изображение — просто необязательный хранимый атрибут (URL или загрузка).
- Интерфейсы на поведенческих границах. Каждый use case — это интерфейс в
  `application` с одним методом, реализованный ровно одним классом. Контроллеры
  и другие адаптеры зависят от интерфейса, никогда от реализации. Порты
  (`CardRepository`, `LeitnerStrategy`) — интерфейсы, объявленные внутренним слоем.
  Мапперы тоже интерфейсы.
- Никаких интерфейсов над данными. Агрегаты, value objects, JPA-сущности, DTO и типы
  `@ConfigurationProperties` остаются конкретными. Интерфейс без поведения и
  с единственной мыслимой реализацией добавляет шум, а не абстракцию.
- Именование реализаций: когда реализацию характеризует её механизм, префикс называет
  его (`JpaCardRepository`, `TokenAuthenticator`, `LeitnerScheduler`).
  Когда сказать нечего, кроме "единственная реализация", используется префикс `Default`
  (`DefaultCreateCardUseCase`, `DefaultCardMapper`).
- Домен никогда не вызывает `Instant.now()`. Время поступает как параметр или через
  внедрённый `java.time.Clock`.
## Тестирование

- JUnit 5 (по умолчанию в Spring Boot). По глобальным стандартам: юнит-тесты домена и use
  cases без контекста Spring; интеграционные тесты адаптеров на реальной инфраструктуре
  (Testcontainers), как только появится хранение.

## Вне объёма (MVP)

См. `PROJECT.md`. Вкратце: никакого AI-пайплайна изображений, никакого шаринга и подписок,
никаких продвинутых SRS. Не создавай этого.


## Bash
- Запускай одну простую команду за вызов, не объединяй действия через `;`, `&&`, циклы и `$(...)`.
- Для поиска и чтения используй инструменты Grep/Glob/Read, а не grep/cat/head в bash.
- Файлы создавай и меняй через Write/Edit, а не через `>` и `sed -i`.
- Если нужна сложная логика, сначала сохрани её как скрипт в файл (например, scripts/sync-specs.sh), или вообще создай себе рабочую директорию, которая не поаде в гит, потом запускай его одной командой.
