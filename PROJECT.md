# Mneme — Обзор продукта и объём MVP

**Mneme** — приложение для изучения слов, построенное на личных мнемонических ассоциациях.
Базовая единица — карточка: слово + перевод + ассоциация, написанные пользователем;
изображение необязательно. Этот документ описывает объём на уровне продукта; MVP
реализуется в сервисе **mneme-core**.

Примечание о языках: **Word** — на изучаемом языке (английском); **Translation**
и **Association** — на родном языке ученика (русском).

Пример идеи: `surround` → перевод "окружать" (to surround) → ассоциация
*"сир, нас окружают"* (рыцари кричат СИР / "sire" + раунд / "round" = круг).
Ассоциацию придумывает человек — в этом весь смысл продукта.

---

## 1. Обзор и цель

- **Что:** инструмент для запоминания слов через ассоциации с индивидуальным
  процессом повторения.
- **Аудитория:** небольшое число пользователей в доверенном кругу (семья).
- **Двойная цель:**
    1. рабочий продукт для ежедневного использования автором и семьёй;
    2. полигон для оттачивания архитектуры (Clean Architecture, ports & adapters,
       мышление в терминах распределённых систем, deploy/k8s).

## 3. Глоссарий (единый язык)

| Term | Значение |
|---|---|
| **User** | Пользователь. Владеет своими карточками и своим прогрессом. |
| **Card** | Единица изучения. Завершена, когда есть Word + Translation + Association. |
| **Word** | Изучаемое иностранное слово (изучаемый язык, например английский). |
| **Translation** | Перевод слова (родной язык ученика). |
| **Association** | Мнемоническая ассоциация. Свободный текст на родном языке ученика. **Всегда пишется человеком.** |
| **Image** | Необязательное изображение карточки. В MVP — только вручную (загрузка/URL). |
| **Visibility** | Видимость карточки: `Private` (по умолчанию) или `Public`. |
| **ReviewState** | Состояние повторения карточки для пользователя. |
| **Leitner Box** | Номер ящика в системе Лейтнера. Определяет интервал повторения. |
| **Review Session** | Сессия повторения: карточки, срок которых наступил. |
| **Grade** | Оценка ответа. **Бинарная:** `Correct` / `Incorrect`. |

*(В Phase 2 добавятся: `ImagePrompt`, `PromptRefinement`, `GeneratedImage`, `AI Service`.
**Эти термины не используются в коде MVP — не вводи для них классы, поля или таблицы.**)*

## 4. Доменная концепция

- Карточка **уже является готовым продуктом** в момент, когда заполнены Word, Translation и
  Association. Изображение — необязательное обогащение.
- **Ассоциацию всегда пишет человек.** Цель — построить личную нейронную связь в голове
  конкретного пользователя. Система **никогда** не генерирует учебный контент.
- **Путь обучения индивидуален:** у каждого пользователя свои карточки и свой
  прогресс. Совместного (группового) изучения нет.
- Карточка принадлежит ровно одному владельцу (**siloed**).

---

## 5. Объём MVP (mneme-core)

- **Идентификация пользователей** и простая аутентификация.
- **CRUD карточек:** создание, чтение, обновление, удаление.
  Поля: Word, Translation, Association, необязательное вручную прикреплённое Image
  (загрузка или URL), флаг Visibility.
- **Повторение по Лейтнеру:** у карточки есть Box и дата следующего повторения; Review
  Session показывает карточки, срок которых наступил; бинарный Grade;
  `Correct` → перевод в следующий ящик, `Incorrect` (в любом ящике) → сброс в
  первый. **В последнем ящике `Correct` оставляет карточку там**, и она продолжает
  повторяться с максимальным интервалом — отдельного состояния "выучено" в MVP нет.
- **Редактирование любого поля карточки не затрагивает ReviewState.** Сброс прогресса —
  отдельное явное действие, и в MVP его нет.
- **Прогресс у каждого пользователя свой** и не разделяется.
- **Флаг Visibility хранится** (по умолчанию `Private`), но **никакая логика на его основе
  в MVP не реализуется**: нет эндпоинтов шаринга, нет запросов с фильтрацией по видимости.
  Это поле — задел для Phase 2.

---

## 6. Вне объёма MVP (НЕ создавать)

- Пайплайн AI-генерации изображений (обогащение промпта, подтверждение, Kandinsky).
- Отдельный AI-сервис (`mneme-ai`).
- Шаринг, подписки, копирование публичных карточек других пользователей.
- Продвинутые алгоритмы SRS (SM-2, FSRS).
- Отдельная сущность "словарь / очередь слов на потом".
- Всё, что явно не перечислено в разделе 5.

## 7. Phase 2 (направление развития, сейчас не реализовывать)

- **`mneme-ai` — AI Service как отдельный bounded context (свой репозиторий).** Поток:
  Association карточки → обогащение в развёрнутый промпт изображения (**GigaChat**) →
  возврат пользователю на редактирование/подтверждение → при подтверждении генерация
  (**Kandinsky**) → изображение прикрепляется к карточке **асинхронно**, пользователь
  получает уведомление о завершении (способ уведомления — TBD, см. §12). У карточки
  появляется конечный автомат генерации изображения.
- **Внешние сервисы Phase 2:** GigaChat — обогащение промпта изображения; Kandinsky —
  генерация изображения.
- **Клиенты:** `mneme-web` (веб), `mneme-mobile` (мобильный). Каждый владеет своими DTO,
  сгенерированными из контракта `mneme-core`.
- **Шаринг:** публичные карточки видны другим; понравившуюся можно скопировать в
  свой набор (она становится вашей карточкой — каждый строит свою связь).
- **Продвинутые SRS** (SM-2 / FSRS) за той же абстракцией планировщика.

## 8. Нефункциональные требования

- Приложение для небольшого доверенного круга — **пропускная способность не является целью.**
  Не оптимизируй под высокий RPS.
- **Задержка синхронного пути:** открытие и прохождение карточек должны ощущаться
  мгновенными (цель p95 ~100–200 мс). Это определяет запросы и индексы, а не
  горизонтальное масштабирование.
- **Сохранность:** коллекция карточек не должна потеряться. Резервные копии — реальное
  требование.
- **Независимость ядра:** домен должен полностью работать без какой-либо AI-интеграции
  (генерация изображений необязательна и не входит в MVP).
- **Готовность к асинхронности (для Phase 2):** работа AI асинхронна, выполняется по
  принципу best-effort, идемпотентна (безопасна для повтора), с таймаутами и потолком
  расходов на внешние API. Создание карточки никогда не блокируется генерацией изображения.
- **Доступность:** "работает, когда член семьи садится заниматься". HA и
  multi-region не нужны.

## 9. Технические ограничения

- **Язык / фреймворк:** Java 21, Spring Boot 4.1.
- **Сборка:** Gradle (Kotlin DSL).
- **БД:** PostgreSQL.
- **Обязательный стиль:** Clean Architecture с явными ports & adapters; домен
  независим от фреймворков и вендоров. Детальный дизайн создаётся в
  `ARCHITECTURE.md`, а не здесь.

---

## 10. Архитектурные инварианты (обязательны; детальный дизайн — отдельный шаг)

- Слои domain и application не зависят от внешних слоёв. Фреймворки (Spring, JPA, HTTP)
  и внешние сервисы — детали на границах.
- Внешние системы находятся за **исходящими портами** (интерфейсами, объявленными внутренним
  слоем); адаптеры их реализуют. В MVP такая система одна — Postgres.
- В MVP `Image` — **необязательный хранимый атрибут карточки** (URL или загруженный
  файл), задаваемый непосредственно пользователем. **Порта генерации изображений в MVP нет.**
  Phase 2 вводит исходящий порт `ImageGenerator`, адаптер которого вызывает `mneme-ai`;
  ядро от него не зависит.
- Алгоритм планирования повторений — **доменная Strategy** за интерфейсом,
  **а не порт** (за ней нет внешней системы). Интерфейс спроектирован
  **строго под нужды MVP (Лейтнер)**; обобщения для будущих алгоритмов — только
  если они нужны сейчас. YAGNI важнее умозрительной гибкости.
- Многопользовательность: `UserId` входит в домен с самого начала и поступает в
  слой application как **явный параметр use case** (не извлекается из
  `SecurityContext` внутри домена или use case). Извлечение из механизма аутентификации
  происходит на границе, в REST-адаптере; сам механизм аутентификации —
  заменяемая деталь.

## 11. Принятые решения и отвергнутые альтернативы

**Изолированные карточки (у каждого пользователя свои)**
- Почему: ассоциация — это личная нейронная связь; разделить можно было бы только
  объективные Word+Translation, что противоречит замыслу и не стоит разделения
  агрегата.
- Отвергнуто: общий набор карточек.

**Лейтнер для MVP**
- Почему: простой, чистый домен; алгоритм находится за абстракцией, поэтому заменить его
  позже дёшево.
- Отвергнуто: SM-2 / FSRS на старте.

**Ассоциации пишет человек**
- Почему: сгенерированные AI ассоциации убивают учебную цель; качество межъязыковых
  фонетических мнемоник от современных LLM ненадёжно.
- Отвергнуто: автоматическая генерация учебного контента.

**Генерация изображений — необязательная и в Phase 2**
- Почему: самый большой множитель сложности (два внешних сервиса, асинхронный пайплайн,
  конечный автомат), и она не входит в цикл обучения.
- Отвергнуто: генерация изображений в MVP.

**Работа AI — отдельный bounded context (`mneme-ai`)**
- Почему: изолирует медленные и ненадёжные внешние вызовы от быстрого синхронного ядра.
- Отвергнуто: встраивание логики AI в ядро.

**Много репозиториев, без общих библиотек моделей**
- Почему: жёсткие границы сервисов; позволяет изучать deploy/k8s и полиглотные сервисы;
  контракты через OpenAPI/spec, каждый сервис владеет своими DTO.
- Отвергнуто: монорепозиторий; общая библиотека доменной модели для всех сервисов.

**Простая аутентификация для MVP**
- Почему: доверенный семейный круг; идентификация моделируется сейчас, аутентификация
  усиливается позже.
- Отвергнуто: полноценная аутентификация (OAuth и т. п.) на старте.

## 12. Открытые вопросы для шага архитектуры

- **Параметры Лейтнера:** число ящиков и интервалы по ящикам (настраиваемые,
  значения по умолчанию TBD).
- **Хранение:** схема БД, границы агрегатов, библиотека хранения (JPA vs JDBC
  vs jOOQ), отображение (без протекания JPA в верхние слои — по стандартам кода).
- **Поверхность API:** форма REST-контрактов (версионируются под `/v1`), DTO vs доменные
  модели на границе.
- **Механизм аутентификации:** Basic или статический токен на пользователя; заведение
  пользователей (seed или самостоятельная регистрация).
- **Развёртывание AI Service (Phase 2):** отдельный процесс или внутрипроцессный асинхронный
  воркер; транспорт (REST/messaging).
- **Способ уведомления о готовности изображения (Phase 2):** polling / SSE / WebSocket / другое —
  TBD. На архитектуру MVP не влияет.
- **Резервное копирование и восстановление** для требования сохранности.
